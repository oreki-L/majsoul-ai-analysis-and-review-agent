## 结论

**复盘模式可以使用官方托管的 Mortal，不需要下载官方权重。** 官网明确提供雀魂牌谱 URL 和自定义天凤 JSON 输入，以及 Mortal 4.1a / 4.1b / 4.1c 等模型选择。这与实时局面 API 或本地权重接入是不同路径。

推荐分两步：先提供“打开官网复盘”，再研究“用户保存报告 → 导入本项目 → 定位决策 → LLM 解释 / 追问”。前者有明确网页支持，实现成本低；后者技术上可设计，但当前公开网页没有承诺稳定的机器读取合同，需要报告样本和解析验收。

不宜把官网表单 `/review` 当作已经开放、可供扩展自动批量调用的 API。目前未找到第三方 API 文档、自动化额度或报告二次处理的明确授权说明；这些是自动集成的待确认项，不能用仓库开源许可证替代在线服务条件。


脚本中未看到通过同类查询参数预选玩家、网络或自定义 JSON 的实现，不能据表单字段名猜测 GET 参数有效。可在本项目复制这些选择供用户对照，但首版仍由用户在官网确认。

## 方案 A：链接跳转，优先落地

在“牌谱复盘”增加“官方 Mortal”入口，由用户填写 / 粘贴雀魂分享链接，预览目标网站，点击后打开上述预填页面。在官网选择玩家与网络、完成验证并提交，结果仍在官网查看或保存。

这条路径不需要本地 Python、Rust、权重、官方 API key 或扩展对官网的跨域读取权限。打开普通链接不等于赋予扩展读取报告的权限。

项目当前 controller 的 `contextIdentity.matchId` 是本地隔离身份，不能当成雀魂牌谱 ID。检查到 `protocol.recordResponse()` 的 `url` 是响应中的数据字段，也不能未经核实当成用户分享链接。首版让用户输入分享链接，后续若要自动获取，需单独确认来源字段及协议，不根据本地 ID 拼链接。

本方案能提供官方模型复盘入口，但尚不能兑现“在本项目里解释官方结果”。界面必须明确这一阶段的范围。

## 方案 B：本地生成全场 JSON，作为补充入口

官网有自定义天凤 JSON 输入，可借用当前 NAGA 导出底层的转换逻辑，但不能直接把 NAGA 文本粘贴过去：

- 当前 `MJNagaReplay.fromObservation()` 输出逐局对象 `rounds[i].json`，每份对象仅有一个 `log`，以及逐行 `tenhou.net/5/#json=...` URL。
- Mortal 自定义输入需要的是 JSON；建议新增全场导出层，按原顺序合并所有小局 `log`，保留一致的规则和座位身份，输出一份可复制 / 下载的对象。
- 当前 NAGA 转换会单独拒绝不支持的小局，但允许导出其余局。这不适合直接标成“完整半庄”：任何拒绝或缺失都应阻止完整模式导出，不能静默删局再拼接。
- 当前转换器拒绝双响 / 多家和牌、途中流局、包牌、流局满贯等情况，14 张庄家配牌也有首弃摸切要求。真实牌谱覆盖率可能受此影响；不能只因两者使用天凤格式就宣称已兼容。
- `mode=replay` 且记录连续不等于整场完整：还需确认从整场开局到明确整场结束、局间点数与供托衔接、半庄规则以及四家牌数据完整。
- 导出包含四家初始暗牌、摸打、里宝牌和结算，属于完整复盘资料，需单独预览并由用户主动提交；不与实时分析的自家手牌 / 公开信息授权混用。

匿名化在这条路径更可控：可沿用 Player 1–4 座位标签，不保留账户、昵称或原始报文。使用原始雀魂 URL 的路径则由官网自行取谱，本项目不能承诺其匿名处理、保存范围或后续数据用途。

建议优先原生雀魂链接，减少转换损失；全场 JSON 作为无法使用链接或需要匿名化时的补充。两条路径均尚未通过本项目真实牌谱线上提交验收。

## 方案 C：导回官方结果，由 LLM 解释

产品目标可以组织为：

```text
完整已结束牌谱
  → 用户在官方网页提交，使用官方 Mortal
  → 保存报告或取得明确支持的结构化结果
  → 本项目导入、核对模型 / 玩家 / 原牌谱并建立决策映射
  → 选中一巡：官方首选 + 实际动作 + 本地证据
  → LLM 解释与独立追问
```

### 报告格式目前的证据

本轮读取 README 链接的[公开示例报告](https://gh.ekyu.moe/mjai-reviewer-demo.html)。这是 **2023-03-07、mjai-reviewer 1.5.3、Mortal 3 的 Classic 报告**，不能当作当前 4.1 / KillerDucky 报告样本。

示例中可看到模型 tag、玩家 ID、局数与本场、每个分析条目的推荐 / 实际动作、候选分数、局部牌谱 JSON 和保存网页入口。它是渲染后的 HTML，包含脚本和牌面 SVG；没有据此确认官网提供独立 JSON 下载或稳定的 DOM 数据协议。

另外核对 `mjai-reviewer/src/main.rs` 和 `src/render.rs`：开源 CLI 确实支持 JSON 输出，其序列化 View 包含 `engine`、`player_id`、`review`、`mjai_log` 等，Mortal review 条目包含 `expected`、`actual`、`details`。**CLI 支持 JSON 不等于官网开放 JSON endpoint 或下载按钮**，也不使本地 CLI 自动取得官网权重。

建议优先研究官网当前是否提供用户可下载的结构化格式；若没有，可做按已知版本适配的“导入已保存 Classic HTML”。KillerDucky 需独立真实样本，不把它当成 Classic 的样式变体。明确列出支持版本，未知格式返回不支持，而不是模糊抓取页面文字。

### 对齐和数据边界

导入后创建独立的 `official-mortal-review` 记录，保存来源、实际 model tag、网络选择（若可确认）、报告版本、视角、牌谱指纹、规则、温度及解析版本。用户填写的 4.1b 标签不能替代报告内部的可核验来源；缺失元数据应标未知。

使用局数 + 本场 + 事件序列 / 动作上下文来匹配本地游标，还要核对牌河、手牌、座位及实际动作。只凭“第 7 巡”不能定位：摸牌、他家弃牌响应、鸣牌后弃牌、立直宣言可能共享巡目。缺失或歧义条目保持未匹配，不随意贴到另一巡。

已有 `engine-result` 合同针对实时局面，要求实时同一步和牌资格；不能不加区分地复用它校验官方离线结果。建议建立复盘导入合同，验证动作、当时可见局面和来源一致性；官方结论作为外部参考保存，不将离线报告转成实时可执行资格。

虽然完整报告包含终局和四家暗牌，LLM 默认只接收该决策时的自家可见信息、本地证据、官方最终建议及对应候选。导入器需要先生成截至该点的可见局面；不能直接把整份报告 / `mjai_log` / `split_logs` 发送给 LLM。若另做“事后全知视角”功能，应独立标记，不能混成当时决策理由。

### 解释和展示

沿用既定方向：官方 Mortal 给答案，LLM 给教学解读，并允许围绕冻结决策继续追问。首选取报告的最终动作，不使用候选最大 Q 值覆盖它；FAQ 明确最终动作与候选表可能因规则修正而不同，应以前者为准。

Q 值和 softmax 只能作为相应模型下的分数 / 偏好参考，不能展示为放铳率、正确率或精确损失。不同网络的 rating 不可直接比较，建议默认不以它作为用户水平评分。解释应引用本地向听、进张及现物、筋、壁等事实，不能称为 Mortal 的内部思考过程。

现有 `decision-discussions.js` 可承接冻结追问，`postgame-review.js` 可组织索引；需要扩展记录来源及官方决策的映射。官方报告覆盖和项目自己采样的建议应分别计数，不将二者混成全场 100% 分析覆盖。导入一次后按需解释具体决策，避免默认对全场每一步调用收费 LLM；整场总结是另外一笔显式请求及预算。

### HTML 与权限

导入 HTML 时只解析白名单数据，不执行脚本、不复用报告 DOM 或牌面素材、不加载 iframe / 外链。建议在不联网的解析路径处理并限制文件大小、深度和条目数，再由本项目组件渲染净化结果。保存的网页仍可能引用外部资源，不能承诺原网页永久离线可用。

首版使用用户选择的本地文件，避免依赖跨站自动抓报告或广泛官网 host permission。未来若要在官方报告页加“发送到本项目”按钮，需要单独的限定域名 content script、用户动作和数据校验；这属于可选集成，尚未实现，也未验证在线服务对此用途的约定。

## 为什么不直接自动 POST 和抓取

官网网页表单不等于面向第三方的 API 合同；Turnstile 是正常提交流程的一部分。自动创建任务、批量请求、轮询、长期抓报告和二次处理需要进一步确认服务支持、额度及条件，不应依靠模拟表单规避验证。

本轮页面中未找到明确的报告二次处理 / LLM 使用条款，也未找到公开 API 文档。这是信息缺口，不是已经存在明确禁止条款；也不能反推为许可。普通打开官网与用户自行使用已有公开流程可先落地，深度自动化应在明确接口和使用条件后再评估。未联系维护者或发送任何消息。

## 建议实施顺序与验收

1. **官网入口**：在牌谱模式提供链接输入、官网预填跳转、玩家 / 模型选择说明、四麻半庄限制及 15 天保存提醒。不改变实时模型配置。
2. **导入试验**：用户按正常流程取得当前 4.1 Classic / KillerDucky 报告，核对数据导出能力与二次处理条件；选定一种明确格式，先建立报告合同、牌谱匹配和游标映射。
3. **LLM 教学闭环**：只针对已匹配条目调用解释模型，保留官方动作、冻结追问、用量及失败重试；报告已导入后不依赖官网在线存在。
4. **全场 JSON 补充**：抽取 NAGA 转换的公共天凤数据层，新增完整半庄校验和全场导出，真实提交验收后再标支持。
5. **自动化**：只有取得可依赖的接口与条件后，才考虑直接提交、轮询和自动回读；不是前四步的必要条件。

重点验收：原始雀魂链接正常受理；目标模型 / 玩家正确；东风和三麻不误标支持；含多本场、吃碰杠、立直和和牌的报告定位无歧义；无法解析的条目不静默消失；错误牌谱 / 座位报告拒绝绑定；全场未来信息与对手暗牌不进入当时解释；保存 HTML 不执行脚本；解释失败不修改官方首选；刷新恢复不重复调用；报告超过保存期不影响已导入数据；Collector 安装包不增加模型 / 官网页面读取能力。

本轮可确认网页接入路径和结构化设计的可行性；尚不能声称真实雀魂提交、当前 4.1 报告解析、自动回读或 LLM 解释已经验收。
