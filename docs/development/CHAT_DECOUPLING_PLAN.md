# 聊天模块解耦方案

**状态：已在当前工作区实现，未发布。** 基线：2026-11-19，`v0.16.11`，检出 `f9e86892af0a`。本文只调整运行时边界，不改变[现有用户流程](../guides/CHAT_INTEGRATIONS.md)；渠道选型及 GitHub 对标沿用[原接入方案](../research/CHAT_CHANNEL_INTEGRATION_PLAN.md)。真实整场和真实飞书群仍待联调。

**当前实现的边界：** 终局提交后 24 小时是发起投递的上限，不是送达保证；有效期内仍受收件箱容量、订阅、目标版本和主机权限限制。到期不再发起投递，但不保证准时从磁盘清除。收件箱丢弃原因与计数仅在后台进程内维护，进程重启后不保证保留。

## 建议

**保留标准版和可选聊天版两个安装选择；由主模块保存历史和产生终局事件，由聊天模块独立决定是否投递。** 优先修复 `historyCommitObserver` 接管写入的问题：即使聊天状态加载、队列或渠道失效，也不能决定历史能否保存。手动分享继续显式确认，自动推送继续只针对绑定后开打的完整整场，不补发旧局。

沿用同一个 MV3 后台及现有构建分包。比纯内存事件多一个小型持久化收件箱，用来恢复后台重启时还未入队的通知；不引入通用事件总线、新服务、聊天机器人运行时或需要用户叠装的第二个扩展。“独立模块”指可从安装包和依赖图中剔除，不指跨扩展通信。

## 模块与接口

| 模块 | 拥有的职责 | 跨边界接口 |
| --- | --- | --- |
| 主模块：采集、历史、复盘 | 识别连续完整的实时整场，规范化并保存历史；核实复盘归属并投影摘要 | 输入沿用历史提交和采集证据；提供 `readReviewSummary(groupKey)` → `ReviewSummaryV1` 或 `null` |
| 聊天版宿主装配层 | 打开采集事件出口；持有终局收件箱，协调历史与事件的写入；注入摘要读口和 UI 插槽 | 向聊天提供 `listCommitted()`、`ack(id)`、`discardPending()`，只收发事件合同和游标所需标识，不暴露历史仓库 |
| 聊天模块 | 设置、预览确认、订阅与权限、持久投递队列、渠道适配 | 消费 `MatchCompletedV1`；通过既有 CloudEvents Webhook 或飞书消息外发。新增渠道只改聊天侧 |

- `MatchCompletedV1` 是**本地事实，不是发送命令**：`id`、`observedStartAt`、`committedAt`、`sourceRef: {tabId, documentId}`，以及 `{playerCount, roundCount, endReason, finalScores?}`。来源从后台校验过的浏览器 sender 提取；只允许可靠完整的点数。收件箱内部可保存对局引用用于提交核对，读口不返回该引用。来源、内部对局标识及开局时间一律不外发；外部事件仍用已有的 `app.majsoul.match.completed.v1`、安装范围 `source` 与数据白名单。
- `ReviewSummaryV1` 只含摘要版本及 `{scope, roundCount, decisionCount, topics}`。预览与确认都从主模块读口取值，内容或目标版本变化就重新确认。聊天不直接打开 `roundHistoryV1`、讨论库或分析结果；版本仅用于本地合同，不自动增加外发字段。
- 由聊天版入口启用采集证据出口，不再从 `majsoulAddon` 面板对象读取 `observeMatchEnd`。面板只提供按钮或挂载回调，保持操作路径不变。后台入口显式注入上述接口，不再改写共享的 `historyCommitObserver`。

## 终局写入与投递

1. **主模块提交。** 历史写入沿用现有串行化和 sender 校验。仅在规范化后首次确认完整实时整场终局且有连续开局证据时，由聊天版宿主同步投影最小事件。主模块在同一次 `storage.local.set` 中提交历史和收件箱更新；标准版直接写历史，不创建收件箱。收件箱的追加、确认及清理由同一写入所有者串行，不能由两侧各自读改写。这个队列只执行本地操作，不等待聊天初始化、权限检查、IndexedDB 投递或网络。
2. **写入失败优先保历史。** 投影异常、收件箱不可读、损坏或满时，跳过本次事件并继续保存历史；联合写入明确失败时，重试只写历史。只写历史也失败才返回历史保存失败。这不承诺在底层 Chrome 存储卡死或不可用时仍能写入。单次 `set` 减少崩溃窗口，不宣称浏览器提供跨存储事务；恢复时只消费能核实对应历史已提交的收件箱条目，不能核实则不发，不从历史生成事件。
3. **聊天独立领取并授权。** 聊天在启动、收到新的已提交事件通知和已有报警唤醒时尝试消费。只接受当前启用订阅对应的 `tabId` 和 `documentId`，且 `since < observedStartAt <= committedAt`；锁定当前 `subscriptionId`、目标 ID 和目标版本。停订、重绑、关闭、改目标或撤权都不能使旧项改投；实际请求前再次核对订阅、目标版本和主机权限。清理投递时暂停消费，持久化当时的收件箱 ID 快照，以同一批 ID 执行清理及重启恢复，再清理旧投递队列；快照后的新终局仍按当前订阅处理。若快照不可读，则保守全量清空；如果清空后尚未记录完成就中断，恢复时可能再清一次。
4. **先入队，后确认。** 首次持久化确定事件 ID，重启、重复领取和入队重试使用同一 ID、提交时间与事件正文。保留现有持久队列按事件和目标去重；首次终局校验挡住重复历史更新。入队成功后才 `ack(id)`；入队暂时失败保留原项，明确不再有资格的项则丢弃。如果后台在入队和确认之间重启，重复领取不能创建第二条投递。仍不承诺平台端恰好一次：Webhook 由接收端按 `(source, id)` 去重，飞书回执不明则按原策略标记，不盲目重发。

**默认关闭与留存取舍。** 为使核心写入完全不查询聊天状态，可选聊天版即使未订阅，也会在本地短暂写入合格终局事实；聊天确认无匹配授权后即丢弃，绝不联网。建议收件箱初始上限 20 条、最长可投递期限自终局提交起 24 小时，满时丢弃新事件、不挤掉已待发项。过期项在下次本地读写或后台唤醒时清理；浏览器关闭时不承诺准时物理删除。仅记录有界的丢弃原因和计数，不含来源、分数、地址或凭据；底层存储失败可能无法记住诊断，不为补记阻塞历史。标准版不保留任何此类事件。

## 迁移与实施顺序

| 阶段 | 交付与验收 |
| --- | --- |
| 1. 收回写权 | 加入最小终局合同和可选本地收件箱；替换 `persistHistory` 委托，消费复用现有发送队列。故障注入验收通过后再移除旧生产路径；同一次牌局绝不双写两份待投递事件。 |
| 2. 摘要与 UI 分离 | 提取版本化摘要读口；把采集证据开关从面板移到装配入口。用现有分享、绑定、重绑路径回归，UI 无需重新设计。 |
| 3. 固化构建边界 | 补构建闭包和浏览器验收：标准版及 Collector 不含聊天入口、收件箱实现、设置片段或 `alarms`；聊天版保留原渠道和交互。 |

不迁移 `roundHistoryV1`，不改现有设置、密钥、目标版本和已入队投递。**同一扩展 ID 升级**时，对旧 `matchPending` 仅保留单向兼容读取：按原事件 ID、订阅和目标版本消费，成功或无效后清理，不能转成新事件；切换安装目录如产生新扩展 ID，沿用现有导出与迁移限制。回退不扫描历史补发，新收件箱的未投递项不承诺由旧版恢复。

## 放行条件

| 场景 | 必须观察到的结果 |
| --- | --- |
| 聊天初始化拒绝或始终未完成、命令阻塞、IndexedDB 故障 | 同一个聊天版里，核心历史仍能保存、读回和继续写，不等待聊天命令。 |
| 收件箱损坏、满或联合写失败 | 成功完成仅历史写入时，不把它报成保存失败；不发送未提交历史的事件；仅历史写也失败时才报历史错误。 |
| 后台在联合提交后或入队后、确认前被回收 | 启动或报警后恢复原始事件，保持 ID 和正文；不重复建投递，不扫描历史；到期不发送。 |
| 牌局证据与授权 | 三／四麻合格终局可推；普通小局、回放、断线或缺采集、重复终局、绑定前开打、跨文档均不推；停订、清理、重绑、改目标及撤权不让积压改投。 |
| 手动分享与发布产物 | 摘要变化要求重预览；敏感字段不越界；`npm test`、`npm run check`、构建产物检查，以及浏览器合成终局和签名 Webhook 通过。真实整场和真实飞书另记联调结果，不用合成测试替代。 |

后续如果确实需要 Discord、Slack、钉钉、企微等，可在同一合同下增加单向适配器；不为拓展渠道改动采集、历史或模型链路。
