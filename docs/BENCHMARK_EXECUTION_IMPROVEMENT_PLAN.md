# 测试执行器改进计划

日期：2026-10-30；实施更新：2026-10-31。状态：P0/P1/P2/P3 已实现，独立工作树基于 v0.11.1；仅离线合成验收，未启动真实模型测试、发布或改写旧实验。

实现入口为 `benchmark/cli.cjs autonomous`，使用文档见 [自主 benchmark 执行与验收](BENCHMARK_AUTONOMOUS.md)。P0 提供自包含传递依赖冻结包、配置/规则/hash 合同及单账本；P1 接入原工具循环的物理 attempt 重试、合同 hold、Merkle 增量 fsync 证据、排他身份锁、响应重放和监督器；P2 自动冻结输入补测并保留原始轨、自动参考统计与报告；P3 持久盲包队列、可替换编程接口和独立结果导入、来源/引用/六维校验与 HTML 报告。评审导入是独立步骤，不宣称 Node 已能调用 Codex 子代理。供应商账单对账尚需外部凭证，本实现不伪造“账单已核对”。

主展示采用最新口径：质量综合均分 /4 与可评/计划，六维和 gate 折叠；MAKA/GPT 得分率为实际权重总和 / 各点最高可得总和，再求两者平均。原始结果与补测、成功延迟与失败等待、实时/追问/global/repeat 分开；费用包括摘要与失败，未知费用不按零计算。规模验收新增至少 120 点执行/恢复，记录增量日志、对象库、checkpoint、耗时与 RSS；不会为每个 HTTP 复制完整状态到日志或内存。

本计划用于下一轮测试，不改变当前已冻结实验的请求、上下文、重试、评分或预算规则，不启动任何模型调用。当前实验的故障恢复另行保留证据与验收，不因本计划自动重跑。

## 1. 目标与交付体验

用户配置数据、方案、模型、各方案 Key 引用、范围、预算和失败策略后，一次启动。执行器自动完成：

`检查配置 → 冻结运行包 → 调度请求 → 保存结果与用量 → 处理可恢复故障 → 完成已批准范围 → 计算指标 → 生成盲评包 → 导入独立评分 → 输出 HTML / Markdown / JSON 报告`

正常执行不依赖 Codex 聊天持续采样，也不需要人工每半小时分配批次。独立评审可以在请求执行期间并行进行；最终报告必须区分“请求已完成”“评审已完成”和“账单已核对”。

机器关机、休眠和网络中断不可能被本地脚本消除。恢复联网或重新启动后，执行器应能自动接续；超过预算、授权范围变化或无法控制的费用暴露才请求人工处理。

自动运行不代表无限重试，也不代表自动扩大后续阶段。所有范围、参数和处理规则在启动前冻结。

## 2. 现状与需要补齐的部分

现有代码已具有配置化方案、顺序调度、工具循环、结构修复、异步摘要、断点、费用账本、参考评分和基础报告。需要改进的是跨环节的自动编排和故障处理，而不是重新实现请求循环。

| 现状 | 下一轮改进 |
| --- | --- |
| 主请求可以自动发送，但故障后常需人工检查和版本化恢复入口 | 统一作业状态与恢复策略，在冻结范围内自动处理已明确可恢复的故障 |
| 一次未返回 usage 的请求可能阻断整批 | 分开记录账单未知和预算暴露；合同支持时自动全额预留，继续不依赖该结果的作业 |
| 本地文件替换遇到临时占用后需专门修复 | 通用本地重试、追加日志和可重建 checkpoint |
| 独立盲评依靠聊天代理逐批派发 | 持久化评审队列；评审执行端可替换，槽位释放后自动派发 |
| 报告依靠人工启动更新，容易引用旧的停止快照 | 按事件自动刷新，绑定明确的输入快照与生成时刻 |
| 执行依赖工作区中的部分活动源码 | 启动前生成独立、不可变的运行包，避免其他分支合并影响恢复 |

## 3. 配置与冻结合同

新增配置应覆盖以下内容；具体字段名在实现时确定，不将提案当作已支持的配置格式。

| 配置项 | 要求 |
| --- | --- |
| 实验范围 | 数据版本、小局、决策点、方案、重复次数、是否首答/追问/全局分析；默认不越阶段 |
| 模型与 Key | 模型参数和价格版本固定；Key 只使用私有文件或环境变量引用，各方案固定映射 |
| 上下文 | 状态、事件、旧局面、旧建议、摘要策略分别版本化；不随错误临时换策略 |
| 重试 | 按故障类别设置是否重试、次数、退避和最长等待；区分运行内重试与补测 |
| 超时 | 逻辑决策总时限、单次 HTTP 时限、队列等待与恢复等待各自定义 |
| 预算 | 总上限覆盖首答、工具后续、修复、重试、摘要和配置的付费评审；可另设非前台任务预留 |
| 未知费用 | 无法证明费用上界时暂停；可选开启经过验证的合同全额预留策略 |
| 独立评审 | 评分规则、执行端、并发、身份隔离、引用校验、失败策略与自身费用来源 |
| 通知 | 正常安静；完成、不可恢复故障、预算不足或需人工处理时通知 |

启动时检查数据与合法动作、Key 槽位、价格合同、可用磁盘、输出目录、锁和源码依赖。离线检查不调用付费 API；如需在线连通性检查，必须显式配置，并计入预算。

运行包冻结全部传递依赖，包括上下文适配器、工具、校验器、模型配置和数据。清单用哈希绑定，Key 值不进入运行包、日志或报告。独立评审规则单独冻结，不把参考答案复制进模型请求。

## 4. 自动调度与运行生命周期

使用普通 Node.js 作业进程执行请求，持久化队列描述尚未执行、运行中、退避等待、成功、失败和阻断状态。作业 ID 至少绑定运行、方案、重复、小局、决策与角色；物理请求另外分配 attempt ID。

按以下边界调度：

- 同一方案、同一小局保持决策因果顺序；失败后的真实状态与事件不能消失。
- 不同方案不共享模型回答、会话历史或 Key；不同 Key 不视为独立账户配额。
- 实时请求优先，后台摘要和评审使用独立可配置队列；评审不得拖慢被测请求或泄露标签。
- 运行前冻结方案轮换、并发和共享配额规则。断网时暂停准入，不启动一波必然失败的请求。
- 连续临时服务故障触发退避和熔断；恢复探测有次数、间隔和费用记录，不自动切模型或换 Key。
- 请求跑完后等待已发摘要落账，再完成执行阶段；无需人为插入等待来提高摘要命中。

一个轻量监督进程负责检测请求进程退出、记录原因并按策略重启。Windows 的计划任务或后台服务安装为可选部署步骤，默认不修改用户系统的开机启动设置。排他锁必须验证进程身份，不能看到旧锁就直接删除。

## 5. 失败分类和自动处理

不能把所有异常统一成“Request failed”后再猜原因。记录经过白名单筛选的错误类别、HTTP 状态、供应商 request ID、Retry-After、派发状态、持久化阶段与 usage 可用性，不保存敏感 headers、Key 或原始网络异常中的私有内容。

| 故障 | 自动处理建议 | 结果和费用处理 |
| --- | --- | --- |
| 确认尚未派发的临时连接问题 | 退避后重试 | 未发生的请求不伪造 usage；仍记录等待与尝试 |
| 限流或临时服务错误 | 尊重 Retry-After，按冻结规则退避；不能仅凭 429/5xx 假定免费 | 原请求有 usage 就记账；没有 usage 进入未知费用判断 |
| 请求已发但超时、断线或响应无法解析 | 先记录未知费用，再判断能否按合同预留；不得假定服务器没有执行 | 新发请求是新 attempt，可能再次收费；无幂等支持时不承诺恰好执行一次 |
| 401/403、Key 无效 | 阻断相关配置，通知用户；不反复重试、不擅自换 Key | 不将其他方案的 Key 借给失败方案 |
| 明确参数错误、上下文超限 | 标记配置或方案失败；不临时缩上下文或换模型 | 保留失败；修方案后作为新版本实验 |
| JSON/结构不合格 | 沿用预先冻结的运行内修复规则，受同一逻辑时限约束 | 单列首次结构通过和修复后交付，所有调用计费 |
| 内容语义差、MAKA/GPT 得分低、盲评不通过 | 不因低分自动重跑 | 真实失败进入主报告，不能挑最好回答 |
| 摘要调用失败 | 按方案约定回退原文或既定检查点，前台不等待 | 保留失败与费用；是否重新生成按冻结摘要策略处理 |
| 本地暂时文件占用 | 只重试本地写入，采用短退避 | 已成功收到的模型响应不重新发送 |
| 磁盘满、证据无法落盘、账本损坏 | 停止新增付费请求，输出明确恢复指引 | 不能为继续执行丢弃日志、清空账本或覆盖原结果 |

建议下一轮的基础设施重试先采用“初始尝试后最多追加 2 次，指数退避并加抖动”，具体值在启动前确认；这不限制模型正常的工具循环。所有运行内尝试共用逻辑时限与总预算，不能每次重试重置计时。超过时限的恢复性补测另起记录，不冒充原实时首答。

## 6. 未知费用的自动预留

将两个状态分开：

- **账单未知**：没有可靠 usage 或供应商账单，实际收费仍不可确定。
- **预算暴露已覆盖**：有足够证据证明最坏收费上界，并已从剩余预算扣除。

只有启动前启用该策略，并存在冻结且可信的合同，执行器才可自动处理新的未知记录。合同必须绑定供应商、端点、模型、上下文上限、实际输出上限、缓存/非缓存/输出最高单价及其他收费项；不能用平均用量或请求字符数当作可信收费上界。

`已知用量估费 + 全部未知费用保留 + 在途请求预留 + 下一请求最坏费用 ≤ 总预算`

满足以上条件时，为特定物理请求添加一次可审计 hold，保留原始 `usage/cost=null` 和未知账标记。后台摘要的失败终态与前台失败终态都必须有明确恢复规则，不能只覆盖普通首答。

无法证明完整上界、合同已变、存在额外计费、原请求仍在途或预算不足时，暂停并通知。供应商后续对账通过追加调整事件替代原 hold，不能删除原未知证据或重复扣除。失败请求是否重试仍由第 5 节独立决定，添加 hold 不代表自动重发。

## 7. 失败补测与连续上下文

“全部请求完再把失败重跑”适合执行层补测，但会影响上下文实验的因果关系，必须分开统计。

| 类型 | 执行方式 | 能否影响后续原实验历史 |
| --- | --- | --- |
| 原决策尚未结束的运行内重试 | 使用同一冻结上下文，在逻辑时限内追加 attempt | 只允许最终交付的一个结果按原规则进入历史 |
| 后续巡目已推进后的失败点补测 | 使用失败点当时冻结的上下文、工具证据和可用摘要；单独恢复队列 | 不能把补测成功答案插回已完成的后续巡目 |
| 希望验证补测成功后整局的连锁效果 | 从明确检查点另起整局分支或新的重复实验 | 单独记录后续全部回答与费用，不与原运行混拼 |

补测不能看到该巡之后的动作、晚到摘要或独立评审反馈，也不能因原回答低分修改问题。请求没有返回完整结果时，不承诺能恢复供应商内部对话或工具循环，按冻结的安全检查点恢复。

报告分别展示原始结果、含运行内重试的最终交付和追加补测结果；禁止以补测后的成功率替换原首答成功率，禁止多次取最高 MAKA/GPT 分。

## 8. 本地持久化与断点恢复

采用追加事件日志保存作业、派发、响应、usage、账本变化和终态；checkpoint 是可重建的索引，不是唯一证据来源。先可靠保存派发意图和预算预留，再允许发请求；收到响应先保存原始证据，再推进作业状态。

为写入协议定义崩溃恢复规则，包括断行、重复事件、部分 checkpoint 和并发结算。仅对明确的短暂文件占用重试；恢复时验证运行包、事件序号、账本与进程锁。不能因为 checkpoint 缺一项就重发一个可能已经收费的请求。

使用单一账本写入入口避免多个后台任务互相覆盖，关键边界按协议 flush。计时使用单调时钟；跨进程恢复另报等待与恢复时间，不拼接不同进程的单调时间值。

## 9. 自动评分与报告

执行器在任务终态后自动更新派生统计，所有付费任务结算或进入明确未知状态后生成执行报告。MAKA/GPT 权重计算、候选覆盖与可得分分母沿用冻结合同。

独立质量评审通过持久化队列连接可替换执行端：

- 可以导出盲包并导入人工/独立代理结果，或配置具有相应模型权限的评审接口；不假定普通 Node 脚本能直接调用 Codex 子代理。
- 使用现有独立 `gpt-6-sol / medium` 评审要求时，执行端必须具备该模型权限；缺少权限明确标记待评，不静默换模型。
- 盲包不包含方案名、Key、费用、参考权重或其他组回答。评审规则和语义词表从第一批统一携带。
- 自动验证引用、评分范围、严重错误门槛、目标覆盖和来源哈希；格式故障重试不能变成反复要求评审改成通过。
- 评审不可用时，被测请求继续；报告展示缺评覆盖率，不用结构合法代替语义通过。若评审本身付费，独立记用量并纳入配置的总预算。

每次报告绑定同一稳定快照，显示生成时间、范围、计划/已派发/已完成/未派发、缺评、未知费用和供应商对账状态。HTML、Markdown 与 JSON 由同一统计结果生成，避免多份数据不同步。

重点展示：

- 首次结构通过率、最终交付率、独立质量通过率和六维均分；有无评审的分母明确区分。
- MAKA/GPT 各自首选一致率、候选覆盖、权重得分率及两者平均得分率。
- 逻辑请求到最终交付的均值、P50/P95；失败耗时、退避、恢复等待与全批墙钟总时长单列。
- 每计划点/已派发点的覆盖、每已派发点平均费用、每交付/质量通过结果摊销费用、小局及整批费用。
- 首答、工具后续、结构修复、重试、摘要与评审的用量和缓存命中分别记账，未知成本不计作零。
- 摘要触发、完成、实际消费、回退、晚到未用与失败，以及全部摘要费用。
- 基础设施失败、模型输出失败、缺测和人工干预次数；原始结果与补测效果分开。

主请求结束即可输出“执行结果版”报告；独立评分与供应商账单后续更新版本。只有对应环节完整才标记完成，不以“执行器正常退出”代表模型质量通过。

## 10. 分阶段实现与验收

| 阶段 | 交付 | 验收重点 |
| --- | --- | --- |
| P0：运行合同 | 配置校验、不可变运行包、事件/作业/attempt标识、单一账本 | 修改活动工作区不影响已冻结运行；旧结果不可覆盖；预算与Key映射不漂移 |
| P1：自动运行与恢复 | 请求队列、后台监督、故障分类、退避、合同hold、持久化恢复 | 注入限流/断网/进程退出/文件占用后，无人工干预继续可恢复任务；未知收费有预留且不重发旧成功请求 |
| P2：补测与汇总 | 冻结上下文补测、原始/补测双轨指标、自动报告 | 后补结果不污染原历史，不挑最好回答，费用无遗漏、无双计 |
| P3：评审流水线 | 盲包队列、执行端适配、校验导入、HTML报告 | 并发槽释放后自动调度；无标签泄露，缺评不伪装通过，评审异常不阻断主测试 |

优先完成 P0/P1/P2，先消除需要一直盯着请求的原因；P3 让报告的质量部分也能自动收尾。先用模拟响应和故障注入验证，不消耗真实模型费用。真实小规模验收另行冻结样本、模型、范围与预算，得到授权后执行。

验收场景至少包含：首次即成功、重试后成功、所有重试失败、已收费响应后保存失败、无usage网络中断、后台摘要未知费用、预算不足、401、429/503、重复启动、崩溃后旧锁、同一未知重复hold、合同错配、跨小局/方案污染、补测后历史不回写、评审服务中断、报告中断后恢复。

完成标准：在已冻结策略覆盖的可恢复故障下，一次启动能自动完成已批准范围并生成完整执行报告；不需要人工逐批启动请求、添加单笔hold、分配评审批次或执行汇总命令。不可恢复问题应明确停在哪、保留了什么、需要谁处理。未经配置支持的供应商未知账或严重本地故障仍可能需要人工介入。

## 11. 实施边界

原提案阶段仅新增文档；本次后续实施已获授权，仅改 benchmark、专用测试与使用文档。没有修改产品默认策略、Key 配置、历史结果或旧冻结运行包，没有真实 API 调用、安装系统后台服务、发布或推送。新策略仅由新 `autonomous` 运行的冻结合同启用；真实模型验收仍需另行冻结样本、模型、范围与预算并获得授权。
