# Mortal＋LLM 提示词方向比较方案

日期：2026-11-05。状态：候选提示词与实验设计已保存，未执行真实模型测试或质量评审。产品仍使用 v0.16.3 的解释提示词 v2；此文件不构成新版本发布记录。

本增补将此前“唯一新首答组”的安排扩展为先筛选提示词、再验证最终方案；数据来源、引擎选择、输入授权与故障合同继续沿用。开发实验结果不能合并成原单方案的正式质量通过率。

## 1. 要回答的问题

2026-11-06准备更新：已纳入庄家末张首摸兼容修复；新输入版本保存原snapshot与hash，仅补齐east2-h0、south2-h0、south2-h1首节点的 `selfDrawnTile`。原84点全部通过当前推理前校验，正式开发／验证范围为24／60。历史X-F仍按原输入重评，3个变更点单列为非完整相同snapshot，不能以新事实倒评旧回答。用户进一步同意18个代表性重复点，改为九局各两个固定坐标，另保留3个锚点各两问。新冻结版本与旧版本共用本轮50元总账本；没有发起付费调用。

开局修复后的上一准备版本验收：适配器／benchmark／引擎／教学工作流／状态回归98项通过，`npm run check`通过；当时12重复＋6追问，全量mock为开发96、验证120、补测18，合计234／234交付。该旧记录保留。

18重复的新准备版本 `prepared-representative-v1` 已另行冻结并完成mock：开发96、验证120、补测24，合计240／240交付，补测引擎请求为0；benchmark专项20／20及 `npm run check` 通过。名单含3个庄家首摸、6个鸣后点及2个对手已立直点，逐点事实保存在本地冻结计划。83份历史原答盲包已导出，共用账本支出与预留均为0。真实引擎推理、LLM及评审仍未运行，生产提示词未因mock结果改变。

比较三个优化方向：减少无依据解释、提高教学可读性、减少无效工具调用。以已发布 v2 为基线，先筛方向，再用未用于本轮调参的小局验证；结果不足以支持修改时保留 v2。不能只看总均分，也不能根据几条漂亮回答挑方案。

沿用此前决定：Mortal 固定 Yuchen 582500；被测解释模型沿用历史 DeepSeek Flash 的冻结配置；评审为 `gpt-6.1-sol / medium`。不增加同期纯 LLM 组，历史只参考当前发布使用的 X-F 原答。模型／端点／权重的选择不在本实验中同时调整。

无论存在几个合法候选，是否比较备选均由解释模型按教学价值决定；只有用户明确问比较才要求回应。未主动比较不能单独构成扣分理由。

## 2. 四套冻结候选

可直接用于后续实验的完整文本、字节数和 SHA-256 在 [提示词目录](../../benchmark/prompts/mortal-teaching-20261105/manifest.json)。文件不带结尾换行，hash 按实际 UTF-8 文本计算。基线来自提交 `782378acdd4615d97039aa586aa2f5132d71b32e` 的 `MJEngineExplanation.prompt`。

| ID | 优化方向 | 新增侧重点 | 主要观察 | 需要防止的退化 |
| --- | --- | --- | --- | --- |
| P0 `p0-release-v2` | 已发布基线 | 原文，不加指令 | 当前质量、时延、调用与错误类型 | 作为共同参照，不能临场修补 |
| P1 `p1-grounding` | 事实与理由一致 | 核对实际动作、弃后牌形、玩家与时点，区分事实和可能的取舍 | 牌形／身份／现物／错误合理化是否减少 | 过度保守，只说证据不足而没有有用解释 |
| P2 `p2-coaching` | 教学表达 | 先讲动作与关键依据，再按重要程度解释具体取舍；简单局面可只写一条充分理由 | 套话、重复、答非所问是否减少，可读性是否提高 | 为讲得生动而编故事、长篇泛论或强行比较 |
| P3 `p3-economical` | 工具与内容效率 | 已有同状态事实不重复查询，按需要查询效率／逐家风险，保留足够依据 | 工具次数、总 token、交付时延、冗余 | 为省调用猜测事实、跳过必要查询或答得过空 |

三个候选均为“完整 v2＋一个方向的附加指令”。共同的牌编码、座位、动作阶段、事实边界、只读工具、动作不可改写及 `summary / reasons / limitations` 合同完全相同。没有增加二次纠错、隐藏模型调用、强制内部思考输出或新的 JSON 字段。

这种设计便于观察新增强调的影响，不等于三个方向严格独立。附加指令会增加输入 token；P3 也必须计算这部分成本，不能预设“提示了省调用就一定更便宜”。

实验 ID 与完整 promptHash 单独写入实验 manifest；解析器返回的 `promptVersion: 2` 只表示共同解释合同，不能代替候选身份。生产模块不读取这些文件，本次不新增产品切换入口。

## 4. 执行分两层

### A. 受控解释比较：24点×4套

先完成真实 Mortal 动作校验并保存24点的冻结动作与来源。四套解释均使用同一点的同一动作、同一 snapshot、事实历史、工具定义及预算；初始消息除 system prompt 外逐字一致。不是四次重新抽取引擎动作来比较解释。

为单独观察解释侧重点，这一层统一不传先前的模型教学／建议；已授权事实及事件仍相同。每点独立解释，不把先运行候选的回答塞给下一套，也不向解释器提供历史 X-F 原答。这是明确改变历史条件的**受控组件实验**，不能当作产品连续小局链路或正式首答通过率。

四套之间按决策点轮换派发顺序：P0→P1→P2→P3、P1→P2→P3→P0、P2→P3→P0→P1、P3→P0→P1→P2，循环使用。同一时刻最多一个真实请求；记录冷／热态、缓存与时间，不将服务波动误认成提示词收益。

每个逻辑回答仍用产品 live 上限：非 thinking、最多2轮模型请求、4次只读工具及25秒解释运行预算。此层引擎已预先运行，计时从解释开始，明确不能将其称为25秒端到端交付。

先看全部24点再按第6节选择一个候选；不因前几条答案好就提前选。P0即使未胜出也进入下一层，作为当前产品的同期混合基线。若三个候选均无可信改善，可直接保留P0，终止扩量。

### B. 产品串联验证：P0与一个候选×剩余小局

锁定胜出候选原文后，在验证组分别经过当前 Worker→真实 Mortal→Pi／真实 LLM→保存／阶段消息链路。各分支按原牌谱游标推进，只承接本分支成功的教学历史，使用空用户记忆；不混入另一分支或开发组的回答。

同一小局中保持各自游标顺序，分支之间轮换先后。每点重新经过真实引擎；保存两分支的动作、followUp、身份和输入hash。若引擎动作不一致，仍计入两边的链路机会分母，但该点不能当作“相同动作下的提示词差异”；单列并定位，不让LLM换动作来凑配对。

首个验证小局可用 `east4-h0` 作为串联冒烟，但它是验证组的一部分：不先看评分调 prompt，通过后不重新跑成更好的一遍。系统性接线失败需保留原失败批次，修复后另起版本；不能把已有质量结果继续叫未见验证。

这里25秒使用产品从请求提交开始的原总 timer，包含引擎阶段，不逐HTTP重新计时。消息／保存成功、浏览器真实渲染与真实在线牌局分开报告。浏览器与故障验收沿用原主测试方案，不靠受控组件实验替代。

## 5. 独立评分

新建并冻结 `mortal-teaching/1.0.0` 评审合同，指定 `gpt-6.1-sol / medium`。保留历史评分锚点、严重性和逐字引用要求；旧合同／旧评分原样保存。

- 共同五维：事实准确、理由落地、上下文隔离、校准、可用性，均0–4分。
- `legal_comparison` 为第六维：实际发生比较或用户明确要求比较时适用；其余记 `not_applicable`、score=null，不扣分，也不自动给满分。
- 每份答案保留按适用维度计算的六维合同均分及维度覆盖；**方案排名另用共同五维均分**，避免不同方案比较频率不同而改变均分分母。比较维质量与发生比例单列。
- major／critical须fail；实质未决问题为needs_review。未交付不让评审补答案，也不补成0分后混入质量均分；机会分母的质量通过率仍包含未交付。

盲包一份一答，提供对应时点全部必要的授权事实与已观测工具结果；不提供候选名、system prompt、优化重点、模型身份、其他答案／评分或费用。事实投影规则统一，不能删掉错误句或只截取较好的摘要。盲序预先随机冻结；解释文风可能泄漏来源，不能宣称完全双盲。

候选间比较的评审均用新合同。X-F重评只用于最终混合方案与历史对读，不用来选择哪套混合提示词；不为四套重复评同一份历史原答。只选当前发布方案X-F首遍，39点复跑单列波动参照。

当前 `benchmark/review.cjs` 默认仍是旧模型且强制六维数值和备选比较，**不能直接拿默认队列跑本实验**。本轮已增加独立的 `benchmark/mortal-teaching/review.cjs` 和串联执行器，不修改旧合同。新评审通过导出／导入运行，尚未实际评分；模型与medium强度须有执行元数据证明。

## 6. 选择与迭代规则

### 开发组只筛方向

先排除出现动作改写、未来／对手暗牌泄漏、错绑决策或critical的候选。然后按24个固定机会的质量通过数、共同五维均分比较；以事实准确／理由落地作为主要诊断，另列超时、工具数、token和完整解释耗时。P1／P2／P3不能分别使用偏向自身的不同总评分规则。

预先采用以下保守筛选：候选较P0至少多2个质量通过点、配对赢点多于输点且改善分布在至少2个开发小局，共同五维均分不下降，才视为可进入验证的质量候选。若质量持平，只有在无新增major／critical、必要依据没有减少，且解释p95或有完整usage的配对成本至少降低15%时，才以效率方向进入验证。费用未知时不能判定成本改善。

多个候选满足时按质量通过数、共同五维均分、p95依次排序；仍无法区分时选附加指令更短者。未通过筛选则保留P0，不为必须产出“新赢家”增加调参轮次。

### 验证组决定是否采纳

采用同样证据与比较方法，至少满足：

1. 原硬边界全部通过，critical为0；新增major逐点解释，不允许用整体均分掩盖新严重错误。
2. 按预先冻结的兼容验证机会，25秒内完整交付≥95%，质量通过≥80%。N=30时分别至少29点和24点；N=60时分别至少57点和48点。
3. 质量方向相对P0的净通过点改善至少 `ceil(0.05*N)`（30点为2，60点为3），改善分布在至少2个验证小局，共同五维均分不下降，完整链路p95不高于P0的110%。
4. 效率方向只有质量通过数及共同五维均分均不下降、没有新增major／critical，且完整链路p95或可比的配对成本改善≥15%才采纳。无论哪项改善，时延均须满足第2项；费用未知时不作省钱结论。

以上为本次小样本选择门槛，不是显著性检验或产品SLA。报告必须同时列配对赢／平／输、失败类型及每小局结果，p95附样本数，不只报一个百分比。没有达到采纳条件就保留P0；一两个好例子不构成上线理由。

### 结果出来后怎么优化

按事实／编码、理由与动作矛盾、教学空泛、必要工具缺失、冗余／超时分类，对应修改最相关的一条指令。开发组最多追加一轮定向修订：在验证组揭盲前，只允许基于已见开发错误，对一个候选新增修订ID，并与P0重跑开发组；旧输出和评分保留。这会额外增加48个逻辑解释作业，必须预先计入预算。

不直接把三个附加段落拼成“综合最佳版”。如需组合，组合版作为一个新的修订候选重新验证。进入验证后不再根据验证错误修改原候选并继续宣称同组验证有效；后续改版需要新数据，或明确标为同数据开发复测，不能自动再开一轮全量测试。

最终选定版本再做18点固定首个解释输入重复，以及3个冻结决策各两轮追问（6个问题）。按原数据中可见场景选点，不读取新答案或历史评分；每小局两点，覆盖差异不等于随机抽样或统计代表性，也不预先假定Mortal将采取何种动作。

| 小局 | 固定事件position | 选取侧重点 |
| --- | --- | --- |
| `east2-h0` | 0、68 | 庄家首摸；对手已立直、三副露、赤牌摸入 |
| `east4-h0` | 24、100 | 首次鸣后；较晚牌山、两副露、赤牌摸入 |
| `south3-h0` | 6、58 | 早段闭手；第二副露后 |
| `south4-h0` | 48、64 | 南四鸣后持赤牌；对手已立直 |
| `south1-h0` | 2、68 | 非庄家早段闭手；较晚首次鸣后 |
| `south1-h1` | 10、38 | 续本早段闭手；第二副露后 |
| `south2-h0` | 0、62 | 庄家首摸持赤牌；已有副露的中后段普通点 |

position是冻结事件游标，不是巡数。名单同时保存nodeId、选择理由、牌山余数、自家副露数、对手立直座位、手持赤牌和摸牌等可见事实。固定点缺失、不兼容或重复时拒绝准备，不替补。追问锚点固定为 `east2-h0:0`、`east4-h0:24`、`south4-h0:64`，分别检查开局、鸣后及立直压力下的承接。

重复不回灌正式历史，追问不能重跑引擎；用户明确问比较时检查是否回应，不把追问义务扩展到所有首答。失败保留并复核；这些补测不能替换主批较差回答。全部补测仍在原50元总预算内。
